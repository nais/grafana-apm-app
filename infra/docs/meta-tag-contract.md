# Nais meta-tag contract for frontend telemetry config

> **TARGET LOCATION:** this is a proposal to file as a nais platform issue
> (whichever repo owns HTML delivery / ingress for nais Applications — e.g.
> `nais/nais.io` docs plus an implementation issue against the platform
> component that serves/rewrites app HTML). Until platform buy-in is
> secured, `@nais/apm` reads build-time env as a stopgap (see "Fallback"
> below) — this doc describes the target state to migrate to, not something
> to implement in this repo.
>
> Source: nais/grafana-apm-app#59, "Proposed platform meta-tag contract".
> Referenced again in nais/grafana-apm-app#60 (Phase 1, `app.release`
> alignment with CDN paths). Milestone M1 (target v0.15), Platform track —
> roadmap issue #91 lists it as "Meta-tag contract … filed with the platform
> team; SDK reads build-time env as the stopgap."

## Problem

`@nais/apm` (the planned `@nais/apm` Faro wrapper, nais/grafana-apm-app#59)
needs to resolve, with zero per-app config, which app is running, which
cluster/environment it's in, which release it is, and which collector
endpoint to send telemetry to. Today every team hardcodes this by hand,
which is exactly the inconsistency #59 exists to eliminate. nais already
knows all of this at deploy time — the app doesn't have to.

## The contract

Nais-injected (or app-emitted, see Fallback) `<meta>` tags in the served
HTML `<head>`:

```html
<meta name="nais-app" content="soknad-dagpenger">
<meta name="nais-cluster" content="prod-gcp">
<meta name="nais-version" content="2026.07.03-abc1234">
<meta name="nais-telemetry-url" content="https://telemetry.nav.no/collect">
```

| Tag | Maps to Faro | Notes |
|---|---|---|
| `nais-app` | `app.name` | Must match the value used for grouping in Nais APM (Top Exceptions, ExceptionDrawer). |
| `nais-cluster` | `app.environment` | nais cluster/environment name (e.g. `prod-gcp`, `dev-gcp`). |
| `nais-version` | `app.version` **and** `app.release` | Doubles as the Faro release tag. **Must default to the build commit SHA** — this is the only version identity the nais deployment API (`Deployment.commitSha`, see nais/grafana-apm-app#64) actually carries, and it is the same value used in the source-map CDN path (`infra/docs/source-maps-on-nais.md`). Teams may additionally pass a semver tag, but SHA is the join key across deploy annotations, CDN paths, and this contract. |
| `nais-telemetry-url` | Faro collector URL | Resolves prod (`https://telemetry.nav.no/collect`) vs. dev (`https://telemetry.ekstern.dev.nav.no/collect`) collectors without the app hardcoding either. |

## `@nais/apm` resolution order

`init()` with zero options resolves config in this priority order (highest
first):

1. Explicit options passed to `init()`.
2. These `<meta>` tags.
3. Generated nais config / build-time env (`NAIS_APP_NAME` etc. — the
   current stopgap, see below).
4. Dev fallback: no-op transport + console echo, with a one-time warning.

## Injection options (open — needs a platform decision)

Two ways to get the tags into served HTML, in descending order of
"platform does the work, app can't get it wrong":

1. **Platform HTML rewriting.** Nais (ingress layer, or whatever serves the
   app's `index.html`) injects the tags at request time or at deploy time.
   Zero app-side code; the values are always correct because the platform,
   not the app, is the source of truth for cluster/version/deploy identity.
   This is the recommended target state but requires nais platform-side
   implementation work and is not yet built (per #59: "the `nais-app` /
   `nais-cluster` / `nais-version` meta tags do not exist yet — this PRD
   proposes them as a contract to be implemented platform-side").
2. **Extend `frontend.generatedConfig`.** The nais Application spec already
   has an **experimental** `frontend.generatedConfig.mountPath` feature that
   mounts a generated JS config file into the pod. Meta tags (or an
   equivalent generated JS object `@nais/apm` reads) could ride this
   mechanism instead of HTML rewriting. Marked experimental today — treat
   as a candidate, not a commitment.

### SSR caveat

Both injection options assume nais can see and modify the served HTML.
**This breaks down for SSR frameworks where nais never sees the
document** — e.g. a Next.js app rendering its own `<head>` server-side,
where the HTML nais's ingress passes through is generated by the app
process itself, not templated by the platform. For those apps:

- The meta tags must be emitted by the **app's own SSR layer**, sourced
  from environment variables injected into the pod (which nais already
  does via the Application spec) — this collapses back to the build-time
  env stopgap, just applied at request/render time instead of build time.
- `@nais/apm`'s resolution order already accounts for this: env-based
  resolution is priority 3, so SSR apps degrade gracefully to it rather
  than silently getting no config.
- Open question (unresolved in #59): is platform buy-in for HTML rewriting
  secured at all, and if the answer differs per rendering mode, does the
  contract need to explicitly document "SSR apps: environment injection
  only, meta tags don't apply"?

## Fallback (current state, until this is filed and built)

Until the platform-side contract above exists, `@nais/apm` resolves
`app.name` / `app.environment` / `app.version` / `app.release` /
collector URL from **build-time environment variables**
(`NAIS_APP_NAME` etc.) baked in at build time by each app's own CI. This is
strictly worse than the meta-tag contract (per-app CI wiring, no platform
guarantee of correctness) but unblocks #59 Phase 0 without waiting on a
platform decision. Migrating from env-based to meta-tag-based resolution
should be a no-op for apps once the platform ships the tags, because the
env path simply becomes a lower-priority fallback rather than being
removed.
